# Per-flow backend affinity pinning + endpoint-removal conntrack eviction (Phase 5)

Bead: mayor-aie31.21
Status: decision-input (Shape-3 read-only research); awaiting operator decision
Date: 2026-09-06
Author: worker agent-a86241176a94239ea

## Recommendation (answer first)

Adopt **stored per-flow affinity**: the ingress picks a backend once, on the
first packet of a flow (the `FWD_FLOW` miss), stores the *full* backend
identity (`backend_node_ip` **and** `pod_ip`) in `FWD_FLOW`, and every later
packet of that flow follows the stored pin instead of re-resolving the
backend set. Selection at pin time is a deterministic hash of the flow tuple
over the ready-endpoint set (so an LRU-evicted-then-reaccessed flow re-lands
on the same backend when the set is unchanged).

Pair it with **scoped, event-driven eviction**: when the userspace controller
sees an endpoint stop serving, it deletes exactly the conntrack entries
pinned to that departed pod — `FWD_FLOW` (ingress side, matched on
`value.pod_ip`) mandatory for **UDP**, and `REV_FLOW` (backend side, matched
on the pod IP already in the key) for **both** protocols. No other config
change touches any flow.

Reconciliation rule (the whole tension in one line): **only the removal of
the specific endpoint a flow is pinned to disturbs that flow; every other
config change — endpoint add, topology, traffic-policy, terminating-but-still-
serving — leaves every established flow on its existing pin.** This mirrors
kube-proxy's conntrack reconciler exactly (evidence below).

Confidence: high on the model shape and the eviction table (both track
kube-proxy's shipped behaviour and the u7s dataplane's actual map shapes);
medium on the multi-endpoint `VIP_MAP` representation, which is Phase-5
(mayor-9gr0n) territory this bead deliberately does not settle.

## The tension

Affinity says *do not disturb a live flow on an unrelated config change*.
Eviction says *do disturb the specific flows whose backend is gone*. They are
the same reconciler seen from two sides: a per-endpoint diff where **removal**
of a still-pinned endpoint is the only event that evicts, and every other
event only changes what NEW flows may select.

## Part 1 — the per-flow affinity model

### Today

`try_uplink_ingress` (`crates/servicelb/servicelb-ebpf/src/main.rs:227-246`)
re-resolves `VIP_MAP` on **every** forward packet and writes
`FWD_FLOW[flow] = backend.backend_node_ip`. The `FWD_FLOW` value is only
existence-checked on return (`main.rs:514`, value discarded — see aie31.20).
With one static backend this is invisible. With a real multi-endpoint set,
any change to the selection input immediately moves in-flight packets to a
backend holding no state for the flow → the connection breaks. There is no
per-flow affinity at all.

### Option A — stored affinity pin (RECOMMENDED)

- First packet: `FWD_FLOW` miss → select a backend from the ready set (hash of
  the flow tuple, see below) → store the full backend identity in `FWD_FLOW`.
- Later packets: `FWD_FLOW` hit → **follow the stored pin**, skip `VIP_MAP`
  resolution entirely.
- `FWD_FLOW` value widens from `u32` (node IP) to the full `VipBackend`
  (`{ backend_node_ip, pod_ip }`). This is the identity the eviction pass in
  Part 2 needs, and it is what the return path should carry forward from
  aie31.20's "discarded value" observation — the value stops being discarded
  and becomes the pin.

Properties: **strict affinity** — a backend-set change disturbs zero
established flows except those pinned to a *removed* endpoint (Part 2). This
is exactly nf_conntrack / kube-proxy-iptables behaviour and exactly what the
bead asks for ("chosen once per flow, stored in conntrack, later packets
following the stored choice").

Selection-at-pin-time = a deterministic hash of the flow tuple over the
ordered ready set (rendezvous/Maglev-style), NOT random. Reason: `FWD_FLOW`
is an LRU map; if an established flow's entry is evicted under pressure and a
later packet re-creates it, a deterministic hash re-lands the flow on the same
backend as long as the ready set is unchanged — graceful recovery instead of
a random re-pin that breaks the connection.

### Option B — stateless consistent-hash selection (CONSIDERED, rejected for u7s)

Compute the backend per packet as `maglev(flow_tuple, ready_set)` with no
per-flow storage. Attractive: keeps aie31.20's `FWD_FLOW`-elimination alive,
zero forward-side storage, and UDP endpoint-removal self-heals for free (next
packet re-hashes onto a live backend).

Rejected because u7s's envelope is small clusters (<1000 endpoints, typically
single-digit endpoints per Service). Consistent hashing disturbs ~1/N of
*unrelated* live flows on any set change; at small N that fraction is large
(1→2 endpoints can remap up to ~50% of flows even with Maglev's bounded
disruption). The bead's stated failure — "repointing a VIP mid-connection
breaks the connection" — is precisely the disruption Option A eliminates and
Option B only bounds. Strict affinity wins for u7s; note the cost (Option A
keeps `FWD_FLOW` storage alive, so aie31.20 as written cannot proceed — see
coupling).

## Part 2 — config-change → eviction-trigger table

Derived from kube-proxy's `CleanStaleEntries`
(`pkg/proxy/conntrack/cleanup.go`, k8s master @ `b2ec8b6fefac`,
2026-09-04; cached in `temp/research/kubeproxy-conntrack-cleanup.go`).
kube-proxy's reconciler is **UDP-only** (`entry.Forward.Protocol !=
unix.IPPROTO_UDP { continue }`, and `svc.Protocol() != v1.ProtocolUDP {
continue }`) and deletes any entry to a Service frontend whose reply-src (the
DNAT'd backend) is not in the current *serving* set. Its own comment states
the affinity invariant verbatim: *"Changes to the service should not affect
existing flows, so we do not take traffic policies, topology, or terminating
status of the service into account."*

| Config change | New-flow selection set | Evict existing pinned flows? |
|---|---|---|
| Endpoint **added** (scale-up / new ready pod) | add to ready set | **No** |
| Endpoint **terminating but still serving** (`serving=true, ready=false`) | **remove** from ready set (stop pinning NEW flows) | **No** — flows drain gracefully (graceful termination) |
| Endpoint **removed / not serving** (pod deleted, or `serving=false`) | remove from ready set | **Yes, scoped to that pod** — see UDP/TCP rows below |
| Service **spec** change with no serving-set change (`externalTrafficPolicy`, topology hints, annotations) | unchanged | **No** |
| Service **deleted** | set becomes empty; `VIP_MAP` entry removed | **Yes** — every flow to that frontend (all its endpoints removed) |
| VIP/selector **repoint** (whole endpoint set swapped) | decompose into per-endpoint add/remove | evict **only** flows pinned to endpoints that left; survivors untouched |

Eviction detail for the "removed / not serving" row, by protocol:

- **UDP — MANDATORY.** UDP has no teardown. A one-way UDP flow (statsd-style)
  refreshes its `FWD_FLOW` LRU recency on every packet, so LRU pressure alone
  never reclaims it; without an active delete it blackholes to (or, on pod-IP
  reuse, misdelivers to) the departed pod indefinitely. This is the exact case
  kube-proxy's cleanup exists for. Delete `FWD_FLOW` entries whose
  `value.pod_ip == departed_pod`.
- **TCP — not required for correctness; recommend deleting anyway.** A stale
  TCP pin points at a dead pod → packets dropped → connection resets → client
  reconnects → new flow → `FWD_FLOW` miss → re-pin to a live backend. So TCP
  self-heals at the *connection* level even under strict pinning. kube-proxy
  does not touch TCP. Recommend u7s still delete the stale TCP `FWD_FLOW`
  entries in the same scan for prompt cleanup, but flag as operator's call —
  it is cleanliness, not correctness.
- **REV_FLOW — delete for BOTH protocols**, on the pod's host node. u7s's
  `REV_FLOW` is keyed directly on the pod IP (`other_ip` in the key), which
  kube-proxy's kernel conntrack has no analogue for. Deleting these closes a
  protocol-independent **pod-IP-reuse misdelivery hazard**: flannel can
  reassign a departed pod's IP to a new pod, and a surviving `REV_FLOW` entry
  keyed on that IP would echo the wrong VIP on the new pod's traffic. The
  departed pod generates no more return traffic, so this is pure hazard
  closure + entry reclamation, cheap on the local node.

## How affinity and eviction reconcile (the single coherent rule)

`VIP_MAP` / the ready set is the **selection input** (what NEW flows may pick).
`FWD_FLOW` / `REV_FLOW` are the **pins** (what EXISTING flows follow). They are
independent by construction, and the design rests on keeping them independent:

1. A reconcile write to the selection set (add/terminating/policy/topology)
   changes only what new flows select. It is a live per-key `VIP_MAP` write and
   **never** touches `FWD_FLOW`/`REV_FLOW` — consistent with the aie31.8
   invariant (reconcile is a per-key map write, not a reload; only reload/
   restart resets the LRU maps).
2. The *only* deliberate control-plane write to the conntrack maps is the
   eviction scan, and it is **always scoped to a specific departed pod's
   keys** — never a clear-and-repopulate. Restructuring `VIP_MAP` for
   multi-endpoint must not be implemented as a flush of `FWD_FLOW`.

So: selection-set churn = affinity is preserved; targeted endpoint removal =
eviction fires, and only for that endpoint's pins.

### Mechanism sketch (control-plane, not data-plane)

Eviction is a control-plane event; keep it out of the fast path. On an
endpoint-removal event the per-node userspace controller (already watching
EndpointSlice; every node sees the same event) runs a bounded scan:

- `FWD_FLOW`: iterate keys via `bpf_map_get_next_key`, look up value, delete
  where `value.pod_ip == departed_pod` (and, for the UDP-only variant, where
  the key's proto byte is UDP). O(table size) = O(8192), on a rare event.
- `REV_FLOW`: iterate keys, decode, delete where `other_ip == departed_pod`.
  The departed pod was local, so this runs on its host node.

No secondary pod→flow index (Rule 2: a full scan of an 8192-entry map on an
infrequent removal is simpler than maintaining an index; revisit only if
profiling shows removals are hot). The data-plane fast path stays a single
`FWD_FLOW` lookup — no per-packet liveness check, no per-packet re-resolution.

## Coupling notes for the operator (flagged, not resolved here)

- **aie31.20 (stateless return-path MAC / eliminate `FWD_FLOW`)** — DIRECT
  CONFLICT with Option A. aie31.20's premise ("`FWD_FLOW` stores nothing anyone
  reads") is true today but becomes false the moment affinity ships: the value
  becomes the pin the forward path reads on every packet. Stateless affinity
  is impossible for a symmetric-return LB — the client's packet carries only
  the VIP, so the ingress *must* remember which backend it chose. If Option A
  is adopted, aie31.20's map-elimination is dead; the keyed-MAC idea could
  still be adopted separately to replace the return-path *existence check*
  (the `main.rs:514` lookup), but the map itself stays for affinity. Recommend
  re-scoping aie31.20 to "return-path auth MAC only" or marking it superseded.
- **aie31.11 (flow-table admission control)** — COMPOSES. aie31.11 owns *when*
  a `FWD_FLOW` entry is created (SYN gate / unconfirmed→assured pool / rate
  limit); this bead owns *what* the entry stores (the pin) and *when* it is
  deleted (endpoint removal). "Pick the backend once" == "admit the flow
  once" — the same event. The pin must be written at whatever moment aie31.11
  admits the flow. Note: Option A keeps the forward-side flush-attack surface
  aie31.11 is concerned with (Option B would have removed it), so aie31.11
  remains load-bearing under this recommendation.
- **aie31.10 (richer `POD_TARGETS`)** — CLOSED (PR #1573); `TARGET_PORTS` now
  keys on the front tuple `(VIP:PORT:proto)`, **not** pod IP. So the eviction
  pass does NOT index off `TARGET_PORTS`. The pod identity for eviction comes
  from `FWD_FLOW.value.pod_ip` (the Option-A widening in *this* bead) and
  `REV_FLOW`'s key. The bead's note about "a richer `POD_TARGETS`" refers to
  the pre-fix state; post-fix, the structure that must grow is `FWD_FLOW`'s
  VALUE.
- **aie31.8 (map pinning) invariant** — RELIED ON. Reconcile is a per-key
  write, never a reload, so config changes never reset the LRU maps; eviction
  is the single scoped exception and must stay scoped.
- **mayor-9gr0n / Phase-5 `VIP_MAP` multi-endpoint shape** — OUT OF SCOPE
  here. This decision assumes `VIP_MAP` grows to represent a ready SET with a
  deterministic selection function, but does not pick the representation
  (array-in-value vs. secondary backend-list map). Selection ordering must be
  stable across nodes for the deterministic-hash recovery property to hold.

## Open questions for the operator

1. **TCP eviction: yes or no?** Recommend yes-for-cleanliness; kube-proxy says
   no (relies on reset). Correctness is identical either way. Decide once.
2. **`FWD_FLOW` value widening vs. aie31.20** — accept that Option A ends
   aie31.20's map-elimination? (Recommend yes; re-scope aie31.20 to the MAC.)
3. **Selection function** — rendezvous vs. Maglev hash for pin-time choice?
   Both give the deterministic-recovery property; Maglev bounds disruption if
   u7s ever grows the fallback to per-packet hashing. Rendezvous is simpler
   and sufficient at u7s's endpoint counts.
4. **Eviction scan cost ceiling** — full O(8192) scan per removal is fine at
   the current ceiling; if aie31.11 raises `max_entries` substantially,
   revisit whether a pod→flow index is warranted.
