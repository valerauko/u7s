# ServiceLB flow-table admission control (2026-09-06)

Bead: mayor-aie31.11 — design(servicelb): flow-table admission control

Status: decision-input, no product code changed (read-only Shape-3 audit).
Awaiting operator decision. Scope: `crates/servicelb/servicelb-ebpf/src/main.rs`
`FWD_FLOW` admission on the internet-facing `uplink_ingress` hook.

## Answer

Adopt **option (a), promote-on-bidirectionality**, as the mandatory, protocol-agnostic
foundation: new flows enter a small unconfirmed pool and are promoted into the
protected main table only when the return leg is observed. This closes the cited
flush attack for TCP, UDP, and QUIC with one mechanism. Layer QUIC's
self-authenticating minted-DCID MAC (option b, the anti-DoS half) on top **if and
only if** mayor-g3lag chooses CID-based keying, and enforce RFC 9000 §14.1's
1200-byte Initial minimum when QUIC parsing lands. Reject option (c): a SYN gate is
free to bypass, and SYN cookies require terminating TCP, which this non-terminating
symmetric-return L3 forwarder does not do. Option (d)'s per-source-prefix rate limit
and per-service opt-in are defense-in-depth on top of (a), not alternatives.

**Resulting ceiling (the DONE-WHEN):** split `FWD_FLOW` into two LRU maps —
`FWD_PENDING = 2048` (the only flood-exposed tier) and `FWD_MAIN = 8192` (unchanged
from the doc's sizing row, but now *justified*: admission control makes
"size against legitimate peak concurrency" a valid basis, which it was not while the
single table was floodable). QUIC's main tier stays at the doc's 4096. Memory delta
≈ +2048 × ~120 B ≈ +240 KiB/protocol/node — negligible, consistent with the
declined-resize note's 120 B/entry economics.

## The problem, re-anchored

The bead cites `servicelb-ebpf/src/main.rs:238`; the live path is
`crates/servicelb/servicelb-ebpf/src/main.rs` and the insert has drifted to **line
246** (`FWD_FLOW.insert(flow_key, backend.backend_node_ip, 0)`), immediately after
the `VIP_MAP.get` match at **line 235**. Line 238 today is `let src_port`.

`uplink_ingress` inserts into `FWD_FLOW` on *any* packet that matches a service
front, with no TCP-state check, no SYN gate, no validation. `FWD_FLOW` is
`LruHashMap<TcpFlowKey, u32>` with `max_entries = 8192` (line 167). BPF LRU never
rejects; it evicts strictly by recency. So ~8192 packets from varying
`(src_ip, src_port)` to a service address cycle the whole table in milliseconds, and
every established flow's forward entry is evicted. The failure is silent: the only
current reader is the return-path existence check at **line 514**
(`FWD_FLOW.get(key)?` in `try_geneve_decap_return`, step 7), so an evicted forward
entry turns into a dropped return packet, not an error. Sizing cannot fix this — any
size is floodable when a single unidirectional packet mints a full, evict-capable
entry that competes on equal terms with established flows.

**Scope boundary.** The floodable surface is `FWD_FLOW` on the *ingress* node,
because `uplink_ingress` is the one hook an off-path sender reaches by dialing
`NODE_IP:SVC_PORT`. `REV_FLOW` (backend, line 436) is only written by
`try_geneve_decap_forward`, reachable only via a Geneve-encapsulated `VNI_FWD`
packet — i.e. a forged-Geneve injection, which is **mayor-aie31.20's** threat class
(stateless return-path authorization via a Geneve MAC), not this bead's. This
recommendation therefore scopes admission control to `FWD_FLOW`; `REV_FLOW` inherits
protection transitively once forward admission and Geneve authenticity hold.

## Why the topology makes option (a) clean

nf_conntrack's anti-flush property is a two-tier model: a new tuple is created
`UNREPLIED` with a short timeout; the `IPS_SEEN_REPLY` bit is set when the reply
direction is observed; `IPS_ASSURED` is set once a connection is genuinely
bidirectional (TCP ESTABLISHED with data, or UDP after a stream threshold both
ways). When `nf_conntrack_max` is hit, `early_drop` reaps a *non-assured* entry and
**skips assured ones** — so a spoofed-source flood can only evict other unreplied
entries, never established connections. (Model cited from the netfilter conntrack
implementation — `nf_conntrack_core.c`'s `early_drop`, `IPS_ASSURED_BIT`,
`IPS_SEEN_REPLY_BIT` — from established knowledge, not a fetched doc.)

The wrinkle that usually blocks porting this to an LB is asymmetry: nf_conntrack
sees both directions on one box. **This dataplane also does** — by design. The
forward leg (`uplink_ingress`, client→VIP) and the return leg (`geneve_ingress`
`VNI_RET`, step 7) both run on the *same ingress node*, because the backend echoes
the ingress node's address and Geneve-returns to it (symmetric return, not DSR). So
bidirectionality is observable at exactly the one point that mints forward state.
The return packet at step 7 *is* the proof of bidirectionality, and it is already
handled there. This is what makes (a) a natural fit rather than a bolt-on.

### Mechanism

Forward (`uplink_ingress`):
1. `VIP_MAP.get` (unchanged).
2. `FWD_MAIN.get(key)` — if present, this is an established flow; the LRU lookup
   itself refreshes recency, nothing else to do.
3. Else `FWD_PENDING.insert(key, value)` — the *only* place a new entry is minted,
   and it lands in the small bounded pool.

Return (`try_geneve_decap_return`, step 7):
1. `FWD_MAIN.get(key)` — present → authorized, proceed (as today).
2. Else `FWD_PENDING.get(key)` — present → authorized (first return); **promote**:
   `FWD_MAIN.insert(key, value)` then `FWD_PENDING.remove(key)`.
3. Else → drop (stale/spoofed), as today.

**What it buys.** A flood of spoofed/off-path forward packets only ever touches
`FWD_PENDING`. It can thrash the pending pool — so genuinely-new connections started
*during* an active flood may fail to promote — but established flows in `FWD_MAIN`
are never touched, because a main-table entry cannot be created without a completed
round trip through a real backend, which requires a non-spoofed source that actually
receives the return. Attack cost rises from "8192 spoofed packets, milliseconds" to
"8192 completed round-trips from real, attributable addresses" — orders of magnitude
harder and rate-limitable. This is nf_conntrack's assured-protected property, ported.

**Cost.** One extra lookup on the forward path; one extra lookup + insert + delete on
the *first* return of each flow; one extra map. No loops — verifier-friendly. The
get→insert→delete promotion is not atomic as a whole, but every interleaving is
benign (transient dual-presence or a redundant pending insert, both self-heal on the
next packet); no correctness hazard.

## Pressure-testing option (a) as the sole build (per the bead)

- **Protects established flows?** Yes — established live in MAIN; the flood reaches
  only PENDING; MAIN is unreachable without a real round trip. Correct priority
  (protect established > admit-new-under-attack), matching nf_conntrack.
- **PENDING flush collateral?** New connections during a flood may not promote —
  acceptable, self-heals when the flood stops; identical to nf_conntrack under a full
  table.
- **UDP with no first-packet signal?** (a) needs none — it gates on
  bidirectionality, which request/response UDP has (DNS, QUIC-over-UDP). Its return
  packet promotes it. Fire-and-forget UDP never promotes, which is *correct*: it has
  no return traffic to protect, so it does not need a protected slot; it ages out of
  PENDING. This is precisely why (a) beats a per-protocol first-packet gate.
- **QUIC?** Same — the first server response promotes the flow. See §QUIC for the
  extra self-authenticating layer.
- **Depends on symmetric return.** If return were DSR/asymmetric, bidirectionality
  would not be visible at ingress and (a) would not work. The design is
  symmetric-return, so this holds — but it is a load-bearing precondition to record.

## Why (c) TCP is rejected

A SYN gate ("only create state on a SYN") is free to bypass — every flood packet
carries the SYN bit at no cost — so it provides ~zero protection. SYN cookies are the
real analog, but they require the LB to synthesize a SYN-ACK, drop the SYN, validate
the returning ACK's cookie, and then replay the connection to the backend — i.e.
terminate/splice TCP. That is incompatible with this dataplane's non-terminating
symmetric-return model and its "pod sees the real client IP at L3" invariant. Option
(a) already achieves the useful part of SYN-flood protection (protect established from
new) without terminating TCP, protocol-agnostically — the natural round trip is the
address-ownership proof that a SYN cookie manufactures cryptographically.

## QUIC (option b): a conditional, strictly-stronger layer

QUIC splits into two regimes:

- **First packet (Initial, long header).** DCID is *client-chosen* (RFC 9000
  §17.2.1), not yet LB-minted — so it is not self-authenticating and must be admitted
  via (a)'s PENDING pool like any other first packet. But RFC 9000 §14.1 requires the
  Initial datagram to be ≥1200 bytes and a server **MUST discard** an Initial in a
  smaller datagram. So the LB can cheaply drop undersized "Initials" before touching
  state, and a QUIC flood must carry ≥1200-byte datagrams to masquerade as valid
  Initials — ~30× the bandwidth of a bare ~40-byte TCP SYN (1200/40). This raises a
  *bandwidth*-constrained attacker's cost ~30×; it does not reduce the packet count to
  flush a packet-counted pool, so it is an adjunct to (a), not a replacement.
- **Established (short header, 1-RTT).** The DCID is *LB-minted*. This dataplane
  already mints the DCID (`servicelb-common` `QUIC_DCID_KEY_LEN = 8`; doc lines
  99–102). If it mints it with an embedded keyed MAC —
  `DCID = routing_bits ‖ MAC(routing_bits, node_key)` — then every subsequent
  short-header packet is **self-authenticating**: the LB verifies the MAC with a cheap
  keyed hash *before* creating or touching conntrack state. An off-path attacker
  cannot forge a valid DCID, so spoofed short-header packets fail the MAC and create
  **no state at all** — strictly stronger than (a)'s create-then-evict, because it
  rejects at admission with zero state cost.

RFC 9000 §8.1.2 Retry-token validation is the third QUIC lever, but issuing Retry
packets means the LB parses Initials, mints integrity-protected tokens (§8.1.4), and
handles the retried Initial — L7 QUIC/TLS awareness at an L3 forwarder, as heavy as
SYN cookies and rejected for the same reason. The embedded-MAC DCID gets most of the
anti-DoS benefit for a keyed hash per packet.

**Re-weighing the draft-ietf-quic-load-balancers decline.** The doc (line 108)
declined that draft's richer scheme *on routing grounds* — "worth adopting only past
a single ingress point (chained LBs); this fixed-length prefix suffices for one hop."
The embedded-MAC's anti-flush property is a **separate argument that was not weighed**
in that decline. Adopting a keyed MAC over the routing bits of the already-planned
LB-minted DCID does **not** reopen the routing decline (it is not the draft's per-hop
routing scheme); it adds an orthogonal security property. This is a new argument in
favor of CID-based keying that mayor-g3lag should weigh.

## UDP (option d): defense-in-depth on top of (a)

(a) already contains the spoofed-flood case (established flows safe; only PENDING
churns). The residual UDP concern is a concentrated, *non-spoofed* flood of new flows
thrashing PENDING. Two optional levers:

- **Per-source-prefix rate limit on PENDING inserts** (token bucket keyed on src /24
  or /64). Defeated by spoofed sources — but the spoofed case is already contained by
  (a), so this only needs to keep PENDING usable against a prefix-concentrated
  attacker.
- **Per-service opt-out of stateful conntrack** for pure stateless UDP — a policy
  knob that removes attack surface, not core mechanism.

Both are add-ons; neither is required for the cited attack, which (a) closes.

## The max_entries ceiling as a consequence (DONE-WHEN)

The ceiling now *falls out* of the mechanism rather than being guessed:

| Tier | Map | Ceiling | Basis (derived from the mechanism) |
|---|---|---|---|
| Pending (TCP/UDP) | `FWD_PENDING` (LRU) | **2048** | The only flood-exposed tier. Sized to expected peak *concurrent half-open* connections with headroom, deliberately small because every byte is floodable. A larger PENDING does not defeat a determined flood (attacker just sends more); it only buys legit-burst headroom. |
| Main (TCP/UDP) | `FWD_MAIN` (LRU) | **8192** | Unchanged from the doc's TCP sizing row — but now *valid*: admission control makes "size against legitimate peak concurrency" a correct basis, which it was not while the single table was floodable. Only reachable via completed round-trips, so it degrades gracefully (LRU) at genuine over-capacity, not under attack. |
| Main (QUIC) | QUIC CID map (LRU) | **4096** | Doc's QUIC row, same reasoning. |

PENDING-size reasoning: a handshake sits in PENDING ~1 RTT (sub-ms intra-DC to
~100–300 ms internet). At an aggressive-for-envelope burst of ~10k new conn/s ×
~0.1 s mean time-in-PENDING ≈ ~1000 concurrent pending; 2048 gives ~2× headroom and
keeps the floodable surface at ~240 KiB. This is the one genuine tunable knob;
everything else follows.

**Why two physical maps, not one map with an "assured" flag.** BPF `LRU_HASH`
eviction is *not* predicate-aware — it evicts strictly by recency and cannot be told
to skip assured entries the way nf_conntrack's `early_drop` does. So the two-tier
property *requires* two maps; it cannot be an in-band flag on one LRU map. Keep both
tiers LRU (MAIN too) so genuine over-capacity degrades gracefully rather than
returning E2BIG — consistent with the declined-resize note's "graceful LRU
degradation, never E2BIG" rationale.

## Coupling notes for the operator

- **mayor-g3lag (QUIC CID vs 4-tuple keying).** Decides whether option (b)'s
  self-authenticating DCID-MAC is even available. CID-based → the MAC is a near-free
  add-on (already minting the DCID; mint it with a MAC) and gives outright
  state-creation prevention for short-header packets. 4-tuple pass-through → no minted
  DCID → QUIC gets only (a) + the §14.1 size gate. **This bead adds a new,
  anti-flush argument in favor of CID-based keying** that g3lag's routing-only framing
  did not weigh. g3lag should re-weigh with this in hand.
- **mayor-aie31.21 (per-flow affinity pinning + selective eviction).** `FWD_FLOW`
  becomes the affinity store (pinned backend per flow). The two-tier model means
  affinity is **authoritative once promoted (MAIN), best-effort pre-promotion
  (PENDING)**: the first forward packet pins a backend into PENDING; later forward
  packets read PENDING for affinity until the return promotes the pin into MAIN. Under
  flood, a pre-promotion pin may be evicted from PENDING → the flow re-resolves
  VIP_MAP on retransmit → but since no return has occurred (flow not established), no
  live TCP state is broken; worst case a SYN and its retransmit hit different
  backends, one wins. aie31.21's selective eviction must delete from **both** PENDING
  and MAIN on endpoint removal, and its per-flow value must be carried across at
  promotion. **The admission model and the affinity model share the same two maps and
  must be designed jointly** for value shape and eviction semantics.
- **mayor-aie31.20 (stateless Geneve-MAC return authz).** If the return is authorized
  by a stateless MAC, step 7 no longer *needs* `FWD_FLOW` for authorization — but it
  still performs the **promotion write** on the return, and `FWD_FLOW` survives for
  the aie31.21 affinity role. So aie31.20 and this bead compose: the MAC handles
  authz; the promotion handles anti-flush + affinity protection. (This bead BLOCKS
  aie31.20 and aie31.17: the map structure decided here — two tiers, LRU, per-map — is
  their substrate.)
- **mayor-aie31.17 (unified flow table with an explicit role tag).** The
  pending/main *tier* dimension is orthogonal to the fwd/rev *role* dimension. Since
  `REV_FLOW` is not the floodable surface (see Scope boundary), it likely does **not**
  need a PENDING tier — a unified table would carry the tier only on the FWD role.
  Needs joint design with 31.17 so the role-tag and tier-tag do not fight.

## Open questions for the operator

1. **PENDING size** — accept 2048, or tune? It is the one floodable knob; correctness
   does not depend on the exact value.
2. **QUIC keying (via g3lag)** — go CID-based to unlock the DCID-MAC, per the new
   anti-flush argument? Recommendation: yes.
3. **UDP per-source-prefix rate limit** — build now or defer? Recommendation: defer;
   (a) already contains the spoofed case.
4. **QUIC §14.1 1200-byte Initial gate** — build with (a) or when QUIC parsing lands?
   Recommendation: defer to the QUIC phase; it is cheap.
5. **MAIN map type** — LRU (graceful over-capacity) confirmed, vs plain HASH with
   explicit-eviction? Recommendation: LRU.
6. **31.17 interaction** — confirm tier ⟂ role composition before unifying the table.

## Confidence

Medium-high on **(a) as the foundation**: it is a well-understood pattern that maps
exactly onto the observable-at-ingress bidirectionality this symmetric-return
topology provides, and it is genuinely protocol-agnostic. High that **MAIN stays at
8192** and is now justified. Medium on the **PENDING = 2048** figure — the burst
model is an estimate for a pre-alpha with no production traffic; it is a tunable, not
a correctness value. Medium on **(b2)** — conditional on g3lag and on QUIC parsing
that does not yet exist. All of this is design reasoning; nothing was validated in a
kernel (read-only research), so the confidence is in the design, not in a measurement.
